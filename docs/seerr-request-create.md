# Seerr request creation slice (v3.4.1)

Tagged Seerr source: `v3.4.1` = `69f73a6f1486fdb51b8ddae9a94a8dfb629f461c`.

- `POST /3picFin/Requests` requires an existing authenticated Jellyfin user. Body allowlist: `{ "mediaType": "movie", "mediaId": 123, "is4k": false }` or `{ "mediaType": "tv", "mediaId": 123, "seasons": [1,2], "is4k": true }`. No `userId`, `serverId`, `profileId`, `rootFolder`, tags or quota bypass. TV seasons must be distinct positive integers; this slice deliberately excludes specials and `"all"` so choice is explicit. Invalid/unknown/duplicate keys fail closed.
- Every write maps the Jellyfin GUID via `GET /api/v1/user/jellyfin/:jellyfinUserId`, checks the returned `permissions` bits, then sends `POST /api/v1/request` with `X-API-User` set to that mapped positive ID. The API key alone otherwise acts as admin ID 1 ([auth.ts](https://github.com/seerr-team/seerr/blob/v3.4.1/server/middleware/auth.ts)). Seerr's own [MediaRequest.request](https://github.com/seerr-team/seerr/blob/v3.4.1/server/entity/MediaRequest.ts) independently enforces request/movie/TV/4K permission, quotas, duplicate requests, and blocklists. `Permission.ADMIN` bypasses bits; global or type-specific request bits are OR-combined ([permissions.ts](https://github.com/seerr-team/seerr/blob/v3.4.1/server/lib/permissions.ts)).
- Seerr's [request body type](https://github.com/seerr-team/seerr/blob/v3.4.1/server/interfaces/api/requestInterfaces.ts) marks destination fields optional. Omitting them allows Seerr's default Radarr/Sonarr (normal or 4K) and configured override rules to apply at approval/subscriber processing ([subscriber](https://github.com/seerr-team/seerr/blob/v3.4.1/server/subscriber/MediaRequestSubscriber.ts)). A missing default may leave an approved request without an Arr dispatch; this endpoint does not invent one.
- Seerr [POST route](https://github.com/seerr-team/seerr/blob/v3.4.1/server/routes/request.ts) returns 201 created, 409 duplicate, 202 when no seasons remain, 403 permission/quota/blocklist. Local API returns 201 with only request ID/status, 409 for both duplicate/no-seasons, 403 for denied/unmapped, 400 invalid input, 502 for unavailable/invalid upstream. It never forwards upstream error text or raw responses. Auto-redirect is disabled by the registered HTTP handler.
- TV writes fetch `GET /api/v1/tv/{mediaId}` with the freshly mapped user, require matching show ID and bounded `seasons[].seasonNumber`, and reject the whole selection with 400 if any chosen season is absent. The read is capped at 1 MiB, 1,000 seasons and the shared 10-second timeout. Specials (season 0) remain excluded by this API's explicit input policy. Seerr's `MediaRequest.request` filters already-requested and available seasons for the requested 4K variant, so a valid selection containing some already-requested seasons can still create the unrequested eligible remainder; a selection with none remaining returns 202/409. That authoritative filtering can race the preflight; we do not infer eligibility from browser data or bypass Seerr quotas/permissions.
- CSRF compatibility: Seerr v3.4.1's optional `network.csrfProtection` installs `csurf` before API-key auth ([server/index.ts](https://github.com/seerr-team/seerr/blob/v3.4.1/server/index.ts)); API key and `X-API-User` alone cannot authorize a POST under that configuration. Its GET middleware sets an `XSRF-TOKEN` cookie. When the mapping or TV details GET exposes that cookie, this adapter fails before POST with an explicit 502 `Seerr CSRF protection is enabled; API-key request creation is unsupported.` It does **not** disable CSRF, fabricate tokens, or forward browser cookies. If a proxy strips `Set-Cookie`, a later upstream 403 may be indistinguishable from permission denial; validate proxy behavior in a disposable deployment. Read-only routes remain usable. The pinned default is CSRF off, but request creation with CSRF on is not supported here.
- No automatic POST retry: Seerr has no idempotency key on this route, so a timeout after acceptance is ambiguous. A user-driven retry may receive 409, but cannot guarantee exactly-once across concurrent writes. Do not label a 502 as proof the request was not created. Reconcile from a fresh user-scoped requests read before offering retry in UI. A 201 response's returned ID, not equality with the selected seasons, identifies the created personal request: v3.4.1 trims seasons already requested or available for that variant. If the ID is absent from the bounded first page, the UI reports unknown rather than inferring success from a different request.
- v3.4.1 permits another movie request when the existing request is declined or completed; declined/completed TV requests also do not reserve their seasons ([MediaRequest.ts](https://github.com/seerr-team/seerr/blob/v3.4.1/server/entity/MediaRequest.ts#L191-L236), [season filter](https://github.com/seerr-team/seerr/blob/v3.4.1/server/entity/MediaRequest.ts#L427-L470)). The UI does not treat these historical personal entries as duplicates. Media status 6 is `BLOCKLISTED` ([media.ts](https://github.com/seerr-team/seerr/blob/v3.4.1/server/constants/media.ts)); the upstream write rejects both variants when standard `media.status` is blocklisted. Options suppress both affordances and announce this in the dialog. `status4k` is returned separately so the availability advisory follows the selected variant; request status codes and media status codes are distinct.

All tests use an in-memory HTTP handler; no live Seerr writes or deployment were performed. Integration should verify the Jellyfin auth route and Seerr default server setup in a disposable runtime before rollout.
