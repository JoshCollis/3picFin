# Household Seerr requests (staged)

The administrator's `SharedRequestsEnabled` switch defaults to false and is independent of Home, Discovery assets, and the existing personal request list. The authenticated `GET /3picFin/SharedRequests?page=1` checks a single nonempty Jellyfin user claim against an existing user on every call. Disabled returns 404; anonymous and userless API-key requests are denied. This deliberately discloses request title identity/status even when that title is outside the caller's Jellyfin libraries; it does **not** grant playback or request creation. The browser offers a separate, on-demand Household Requests list, leaving My Requests and its create reconciliation personal.

Seerr v3.4.1 (`server/routes/request.ts`, lines 32–161) restricts list reads to `requestedBy.id = req.user.id` unless the Seerr identity has `MANAGE_REQUESTS` or `REQUEST_VIEW`. Its `server/middleware/auth.ts` maps an API key with no `X-API-User` to administrator ID 1. The shared read uses that server-held key only after Jellyfin authorization and the admin switch; it is **not** a browser identity or authority for POST. Existing personal reads and POSTs continue to map the Jellyfin user and send `X-API-User` with mapped permission checks.

The global source requests 20 records per page, at most 100 pages, with a ten-second operation deadline, a one-MiB response cap and four non-queuing shared read slots. Production HTTP transport disables redirects. The response is an allowlisted request ID/status, movie/TV type, TMDb ID, media status, 4K flag and bounded season numbers plus bounded pagination. No requester/modifier names, emails, Seerr users, Arr destinations, file paths, credentials, or arbitrary upstream JSON are serialized. Errors are sanitized. Shared responses use `private, no-store`.

This is staged, not deployed. `python tests/disposable-shared-requests.py` starts a throwaway Jellyfin 12.1 server and local Seerr stub; the checked run returned 200 with the same allowlisted DTO for two distinct signed-in accounts, 401 anonymous, 403 userless API key, and exactly two server-side global reads without `X-API-User`.

`python tests/disposable-shared-browser.py` builds a **scratch-only pinned** Home adapter (the production fingerprint remains unset), starts disposable Jellyfin 12.1 plus File Transformation, Plugin Pages, Home Screen Sections and the local Seerr stub, and deletes its containers, configuration, generated passwords and library fixtures on exit. It creates disjoint `alice` and `bob` movie libraries, verifies each user's `/Users/{id}/Views` contains only their own library, then signs both into the **same browser page in sequence**. Both explicitly load an identical household title (TMDb #17) while their personal/native library surfaces remain separate. An intercepted second shared read remains pending when Alice logs out; the Fin pane is removed before the held response is released, and no stale TMDb #999 appears after Bob signs in. Home/Fin, Favorites and Search route transitions preserve the native Home/Favorites surfaces and dispose/recreate the Fin panel. The checked browser run passed. Jellyfin navigation can abort the intercepted HTTP request before delivery; the probe additionally holds a browser `ApiClient.getJSON` promise on Bob's mounted panel, changes the current-user identity to null (triggering adapter teardown), then resolves the old promise with TMDb #999 in the still-live page and verifies it never paints after remount. The latter is a controlled promise-delivery test, not a claim that an aborted HTTP response was delivered.

Neither disposable probe proves deployment, arbitrary account-switch integrations, or active Home-bundle attestation. Parity and rollback remain rollout gates.
